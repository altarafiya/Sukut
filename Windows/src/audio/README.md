# WASAPI backend contract

## Current behavior — Step 8 jitter correction

The adapters now use timer-driven shared WASAPI with explicit endpoint IDs and unchanged float32/PCM16 conversion. Requested capacity is 100 ms for capture and 80 ms for render. Capture drains promptly; spare capacity does not make it wait for 100 ms of audio. Render starts after three 20 ms blocks of real audio (60 ms at 48 kHz), with no inserted silence or duplicate frames. A normal finite stream shorter than that reserve starts and drains in Finish. Cancellation stops immediately and discards the queued tail.

This replaces the original minimum-capacity shared event mode. That mode requires zero duration/period parameters and provided only 22 ms capacity on this host. A 20 ms block plus scheduling and inference variation could exhaust it. Timer-driven shared mode permits the larger requested capacity. See [Microsoft client initialization](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-initialize).

Each native owner thread waits on its own 4 ms one-shot high-resolution timer and cancellation event. The timer is supported on Windows 10 version 1803 or later, with a normal waitable-timer fallback for older systems. No global timer-resolution setting is changed. The independent pipeline no-progress deadline, COM ownership, MMCSS registration and error/cancellation contracts remain intact. Legacy event_wakes counts wait-object wakes; these are now timer signals. See [Microsoft waitable timer API](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createwaitabletimerexw).

Snapshots include capture device-position gaps/missing frames, packet timestamp and read intervals, render write intervals, empty-padding observations, actual capacity and startup reserve. These describe the application/driver transport and do not establish acoustic dropout count or end-to-end delay. The render-clock deficit estimate returned zero during a visibly starved baseline on this driver, so it is not an authoritative continuity measurement. Desktop diagnostics store only metadata beside the settings file, once per second on the controller thread; they do not record audio.

The Audio DSP/model are unchanged. The larger reserve explicitly trades some delay for continuity. Listening retest and measured end-to-end delay remain separate from numerical waveform parity and bounded transport checks. Step 8 evidence documents the before/after results; Step 9 is still separately gated.

## Historical implementation and Step 6/7 validation

`cleanwave_audio` enumerates real Core Audio endpoints and implements event-driven shared-mode `WasapiCapture` / `WasapiRender` adapters. It uses explicit endpoint IDs, never speaker loopback. Constructors store configuration; each worker's Open hook initializes an STA COM apartment, client, service and events on that worker. Close releases them on the same thread. The playback worker's Finish hook drains normal EOS; cancellation/failure stops promptly and discards pending playback.

The worker contract is 48 kHz stereo PCM16. WASAPI clients request stereo float32 and the Windows audio engine handles conversion between that client format and the endpoint's mix format. AUTOCONVERTPCM and SRC_DEFAULT_QUALITY enable the built-in channel matrixer/resampler; NOPERSIST and a new session GUID avoid persisting session volume/mute. No endpoint/default/volume/format setter is called. Native mix format and client format are distinct; requesting a format does not alter the system endpoint configuration. [Microsoft stream flags](https://learn.microsoft.com/en-us/windows/win32/coreaudio/audclnt-streamflags-xxx-constants).

Float/PCM conversion clips finite values to the PCM16 range and rejects NaN/Inf. A native capture packet is copied into one preallocated staging buffer and released in full immediately, then exposed through partial stereo-frame reads. Silent packet flags produce exact zeros. An initial discontinuity flag is recorded. Strict clients retain fatal handling for a later discontinuity. Step 7 live clients explicitly opt into resume_on_discontinuity: the first returned frames carry a segment marker and the worker clears context/state before further processing. Timestamp errors are counted without presenting timestamps as valid latency measurements. Render uses current padding and partial writes, then starts only after the first data buffer is queued.

Both streams use event waits with a cancellation event and a stop callback. Waits are bounded to 100 ms, with the worker's independent no-progress deadline. Open/activation and individual audio-service calls are synchronous and are not forcibly interruptible; callers must retain objects until workers have joined. All Read/Write/Finish/Close calls must run on the opening thread. The Step 6 worker hooks enforce this lifecycle. [Capture interface ownership](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nn-audioclient-iaudiocaptureclient), [render interface ownership](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nn-audioclient-iaudiorenderclient).

Default-device changes do not silently redirect an explicitly selected stream. Missing/inactive/wrong-direction endpoints fail before streaming. Device/resource invalidation, service failure, strict-mode capture discontinuity and persistent event starvation propagate as errors; the pipeline retains the first failure and cancels its workers. Re-enumerate, validate a new explicit route and restart after such a fault. Actual unplug/suspend/service-stop tests were not performed in Step 6.

The installed VB-Audio route is validated from active endpoint direction, known CABLE Input/Output identity and the connected adapter's device-instance property. Generic container IDs are not sufficient: this host reports the same root container sentinel for both VB-Audio and Realtek. Topology subdevice IDs also differ between cable capture/render; their parent device-instance identity provides the pairing. The physical output must belong to a different adapter and must not be a VB-Audio render endpoint. The baseline permits the verified USB/HDAUDIO hardware bus classes and rejects other unverified software outputs; Bluetooth/other buses need separate validation before route support. A native synthetic transport test additionally confirms that the selected pair carries independent stereo tones. [Device topology](https://learn.microsoft.com/en-us/windows/win32/api/devicetopology/nn-devicetopology-idevicetopology), [connected device ID](https://learn.microsoft.com/en-us/windows/win32/api/devicetopology/nf-devicetopology-iconnector-getdeviceidconnectedto).

Standalone adapter clients may request rates such as 44.1 kHz to validate Windows conversion; the worker pipeline rejects rates other than 48 kHz. Actual tests used a 48 kHz engine mix with 44.1 kHz client rates in render and capture. Different physical native mix rates, mono/multichannel matrixing and broad device compatibility remain unverified.

GetStreamLatency returned zero for the tested driver clients. That is only the API's reported value; it does not establish zero latency. The allocated 48 kHz stream buffer was 1,056 frames (22 ms). Actual virtual/physical buffering, DSP and end-to-end delay must be measured during later integration. [Client initialization](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-initialize).

The verifier sends its nonzero fixture only to the virtual cable. Its physical HyperX test uses zeros. No Audio model is loaded and no other application's route changes. These tests establish backend operation and conversion, not live AI replacement or listening quality. See `docs/ROUTING.md` for the prepared route and restoration contract.

Step 7 registers native I/O threads with the existing MMCSS Audio task and reverts on their owning threads when sessions close. Registration errors are exposed; no system profile/service setting is changed. [Microsoft registration API](https://learn.microsoft.com/en-us/windows/win32/api/avrt/nf-avrt-avsetmmthreadcharacteristicsw). Step 7 detected HyperX disconnected before startup and used Realtek only after explicit user selection; active-stream hotplug/suspend/service failure remain unrun.
